## Быстрый старт

### Требования

Для запуска проекта требуется:

- Python 3.11 или выше;
- [uv](https://docs.astral.sh/uv/);
- не менее 8 ГБ оперативной памяти;
- локально доступная модель `intfloat/multilingual-e5-large`.

### Установка

Клонировать репозиторий и перейти в директорию проекта:

```bash
git https://github.com/vorobjov89/customs_service
cd customs_service
```

Установить зависимости:

```bash
uv sync
```

### Подготовка embedding-модели

Для dense retrieval используется модель:

```text
intfloat/multilingual-e5-large
```

Перед первым offline-запуском модель необходимо один раз загрузить в локальный кэш Hugging Face:

```bash
uv run python -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('intfloat/multilingual-e5-large')"
```

После загрузки модель используется только из локального кэша. В `predict.py` включён режим `local_files_only=True`, поэтому во время выполнения решения сетевые запросы не выполняются.

### Запуск

Финальное решение запускается из корня проекта:

```bash
uv run python run.py --data ./data --out ./out
```

Чтобы запускать командой

```bash
python run.py --data ./data --out ./out
```
сначала потребуется активировать виртуальное окружение. На macOS/Linux

```bash
source .venv/bin/activate
```

на Windows PowerShell:

```powershell
source .venv\Scripts\Activate.ps1
```

на Windows CMD:

```cmd
source .venv\Scripts\activate.bat
```

В результате создаётся файл:

```text
out/predictions.csv
```

Файл содержит следующие колонки:

- `declaration_id` — идентификатор декларации;
- `rank` — ранг регуляции от 1 до 10;
- `regulation_id` — идентификатор регуляции;
- `score` — итоговый RRF score.

Для каждой декларации возвращается ровно 10 уникальных регуляций.

## 1. Постановка задачи

Требуется для каждой таможенной декларации определить 10 наиболее
релевантных регуляций ТН ВЭД и вернуть их в порядке убывания
релевантности.

На вход подаются:

- `declarations.jsonl` — 120 таможенных деклараций;
- `regulations.jsonl` — 360 регуляций;
- `tnved_knowledge.txt` — дополнительный справочник по иерархии ТН ВЭД.

Для каждой декларации необходимо вернуть ровно 10 уникальных регуляций
с рангами от 1 до 10.

Результат сохраняется в:

`out/predictions.csv`

со следующими колонками:

- `declaration_id`;
- `rank`;
- `regulation_id`;
- `score`.

Во время запуска решение не использует сетевые запросы.

---

## 2. Ограничения

Решение должно запускаться локально из корня проекта командой:

```bash
python run.py --data ./data --out ./out
```

Ограничения:

- время запуска — не более 30 минут;
- оперативная память — не более 8 ГБ;
- допускается использование локальной GPU;
- размер используемых моделей — не более 8 млрд параметров;
- во время оценки запрещены сетевые запросы.

---

## 3. Подход к разработке

Решение разрабатывается итеративно. На каждом этапе изменяется
ограниченное количество компонентов, после чего результат сравнивается
с предыдущей версией на одной и той же локальной validation-выборке.

Последовательность подходов:

1. TF-IDF + cosine similarity;
2. BM25;
3. semantic retrieval с использованием sentence embeddings;
4. комбинация lexical и semantic scores.

---

## 4. Локальная validation-выборка

Поскольку валидационный сет (ground truth) не предоставляется, для разработки была сформирована независимая
локальная из 40 деклараций.

Для каждой декларации вручную определена одна наиболее релевантная
регуляция.

При ручной разметке учитывались:

- описание товара (`G31_1`);
- дополнительное описание (`desc_extention`);
- код ТН ВЭД регуляции;
- описание регуляции;
- иерархия ТН ВЭД из `tnved_knowledge.txt`;
- `explanation`;
- `notes` в неоднозначных случаях.

При определении эталонной регуляции результаты алгоритмов поиска
не использовались, чтобы избежать утечки информации (data leakage).

Validation-разметка используется только для разработки и сравнения
моделей и не используется непосредственно в финальном запуске
`run.py`.

---

## 5. Метрики

Для оценки используются те же метрики, которые указаны в тестовом
задании:

### Hit@1

Доля деклараций, для которых релевантная регуляция находится
на первом месте:

$$
Hit@1 = \frac{\#{i: rank_i = 1}}{N}
$$

### Hit@5

Доля деклараций, для которых релевантная регуляция находится
в первых пяти результатах:

$$
Hit@5 = \frac{\#{i: rank_i \leq 5}}{N}
$$

### Hit@10

Доля деклараций, для которых релевантная регуляция находится
в top-10:

$$
Hit@10 = \frac{\#{i: rank_i \leq 10}}{N}
$$

### MRR@10

Mean Reciprocal Rank для первых десяти результатов:

$$
MRR@10 = \frac{1}{N}\sum_{i=1}^{N}\frac{1}{rank_i}
$$

Если релевантная регуляция не попала в top-10, вклад декларации
равен 0.

Основные метрики для сравнения:

- Hit@1;
- Hit@5;
- Hit@10;
- MRR@10.

---

## 6. Baseline №1 — TF-IDF

### 6.1. Идея

В качестве первого baseline используется классический лексический
поиск на основе TF-IDF и cosine similarity.

Для каждой декларации строится текст из:

- `G31_1`;
- `desc_extention`.

Для каждой регуляции на первом этапе используется только поле:

- `description`.

Поля `notes` и `explanation` намеренно не используются в первом
baseline, поскольку они содержат большое количество дополнительной
контекстной информации и могут вносить шум.

Таким образом, задача сводится к вычислению лексического сходства
между текстом декларации и описанием каждой из 360 регуляций.

Схематично:

```text
Декларация
    │
    ├── G31_1
    └── desc_extention
    │
    ▼
  TF-IDF
    │
    ▼
вектор декларации
    │
    │ cosine similarity
    ▼
┌───────────────────────────┐
│ 360 регуляций              │
│                           │
│ R1    score = ...         │
│ R2    score = ...         │
│ ...                       │
│ R360  score = ...         │
└───────────────────────────┘
    │
    ▼
сортировка по score
    │
    ▼
Top-10
```

### 6.2. Параметры

Используется `TfidfVectorizer` со следующими параметрами:

```python
TfidfVectorizer(
    lowercase=True,
    ngram_range=(1, 2),
    min_df=1,
    sublinear_tf=True,
)
```

Для каждой декларации вычисляется cosine similarity с каждой
регуляцией, после чего выбираются 10 регуляций с максимальным score.

### 6.3. Результаты

На локальной validation-выборке из 40 деклараций получены следующие
результаты:

| Метод  |  Hit@1 |  Hit@5 | Hit@10 | MRR@10 |
| ------ | -----: | -----: | -----: | -----: |
| TF-IDF | 0.3500 | 0.6500 | 0.7250 | 0.4771 |

Требования из тестового задания:

| Метрика | Минимум |     TF-IDF |
| ------- | ------: | ---------: |
| Hit@1   |    0.30 | **0.3500** |
| Hit@5   |    0.68 | **0.6500** |
| Hit@10  |    0.80 | **0.7250** |
| MRR@10  |    0.45 | **0.4771** |

TF-IDF baseline превышает минимальный уровень по Hit@1 и MRR@10,
но не достигает проходного значения по Hit@5 и Hit@10.

Это показывает, что простой лексический поиск уже способен находить
релевантную регуляцию для значительной части деклараций, однако
часто располагает её недостаточно высоко или не находит в top-10.

## 7. Sparse retrieval

После базового TF-IDF был проведён ряд экспериментов с lexical retrieval.
Целью было проверить, насколько качество зависит от способа представления
текста и от предварительной нормализации.

Во всех экспериментах использовались одни и те же тексты:

**Декларация:**

```text
G31_1 + desc_extention
```

**Регуляция:**

```text
description
```

Поля `notes`, `explanation` и дополнительный файл `tnved_knowledge.txt`
на данном этапе не использовались.

Оценка проводилась на локальной validation-выборке из 40 деклараций.

Основные метрики:

- Hit@1 — доля случаев, когда релевантная регуляция находится на первом месте;
- Hit@5 — доля случаев, когда релевантная регуляция находится в top-5;
- Hit@10 — доля случаев, когда релевантная регуляция находится в top-10;
- MRR@10 — среднее обратное ранговое положение релевантной регуляции,
  если она попала в top-10.

### 7.1. TF-IDF baseline

Первоначально был реализован классический TF-IDF retrieval.

Для каждой декларации вычислялось косинусное сходство с каждой регуляцией,
после чего регуляции сортировались по убыванию similarity.

Были проверены word-level и character-level n-граммы.

Результаты:

| Модель               |  Hit@1 |  Hit@5 | Hit@10 | MRR@10 |
| -------------------- | -----: | -----: | -----: | -----: |
| TF-IDF word 1-gram   | 0.3500 | 0.6250 | 0.7000 | 0.4733 |
| TF-IDF word 1–2-gram | 0.3750 | 0.6500 | 0.7250 | 0.4938 |
| TF-IDF word 1–3-gram | 0.3500 | 0.6500 | 0.7250 | 0.4772 |
| TF-IDF char 3–5-gram | 0.5000 | 1.0000 | 1.0000 | 0.7375 |
| TF-IDF char 3–7-gram | 0.4750 | 0.9750 | 1.0000 | 0.7167 |
| TF-IDF char 2–6-gram | 0.5250 | 1.0000 | 1.0000 | 0.7425 |

Character-level представление значительно превосходит word-level
представление.

Вероятная причина — специфика русского языка и предметной области:
один и тот же товар может встречаться в декларации и регуляции в разных
грамматических формах.

Например:

```text
свинина
свиное
свиней
```

Character n-граммы позволяют учитывать общие фрагменты слов без
необходимости выполнять явную морфологическую нормализацию.

---

### 7.2. BM25

В качестве альтернативного lexical retrieval метода был проверен BM25.

Использовалась библиотека `bm25s`.

Результат:

| Модель          |  Hit@1 |  Hit@5 | Hit@10 | MRR@10 |
| --------------- | -----: | -----: | -----: | -----: |
| TF-IDF word 1–2 | 0.3750 | 0.6500 | 0.7250 | 0.4938 |
| BM25            | 0.3000 | 0.5500 | 0.6500 | 0.4227 |

На данной validation-выборке BM25 оказался хуже TF-IDF по всем
рассматриваемым метрикам.

Поэтому BM25 не использовался в качестве основного retrieval-механизма
в следующих экспериментах.

Это также показывает, что в данной задаче стандартные улучшения
классического lexical retrieval не обязательно дают прирост качества:
характеристика текста и способ формирования признаков оказались
важнее выбора между TF-IDF и BM25.

---

### 7.3. Character vs. character-within-word n-граммы

После обнаружения преимущества character-level TF-IDF был проведён
отдельный эксперимент с `analyzer="char_wb"`.

В отличие от обычного `char`, `char_wb` формирует character n-граммы
с учётом границ слов.

Были проверены следующие варианты:

| Модель             |  Hit@1 |  Hit@5 | Hit@10 | MRR@10 |
| ------------------ | -----: | -----: | -----: | -----: |
| TF-IDF char 2–6    | 0.5250 | 1.0000 | 1.0000 | 0.7425 |
| TF-IDF char_wb 2–6 | 0.5500 | 0.9750 | 1.0000 | 0.7458 |
| TF-IDF char_wb 3–5 | 0.5750 | 1.0000 | 1.0000 | 0.7667 |
| TF-IDF char_wb 3–7 | 0.5500 | 1.0000 | 1.0000 | 0.7542 |

Лучший результат среди проверенных конфигураций показал диапазон
`3–5`.

Возможное объяснение — компромисс между слишком короткими
n-граммами, которые могут давать много случайных совпадений, и
слишком длинными n-граммами, которые становятся чрезмерно
специфичными.

---

### 7.4. Нормализация текста

На следующем этапе была проверена базовая нормализация текста.

Использовались следующие преобразования:

1. приведение текста к нижнему регистру;
2. удаление пунктуации;
3. нормализация последовательностей пробелов.

Лемматизация и стемминг не использовались.

Эксперимент проводился поверх лучшей найденной sparse-конфигурации:

```text
analyzer = "char_wb"
ngram_range = (3, 5)
sublinear_tf = True
```

Результаты:

| Модель                             |      Hit@1 |      Hit@5 |     Hit@10 |     MRR@10 |
| ---------------------------------- | ---------: | ---------: | ---------: | ---------: |
| TF-IDF char_wb 3–5                 |     0.5750 |     1.0000 |     1.0000 |     0.7667 |
| TF-IDF char_wb 3–5 + normalization | **0.6250** | **1.0000** | **1.0000** | **0.7937** |

Нормализация дала дополнительный прирост:

```text
Hit@1:  +0.0500
MRR@10: +0.0270
```

Таким образом, простая нормализация оказалась полезной даже после
перехода к character-level признакам.

### 7.6. Выбранный sparse baseline

На основании проведённых экспериментов в качестве основного
sparse baseline выбран:

```text
TF-IDF
analyzer = char_wb
ngram_range = (3, 5)
sublinear_tf = True
```

с предварительной базовой нормализацией текста:

```text
lowercase
→ удаление пунктуации
→ нормализация пробелов
```

Итоговое качество на validation-выборке:

| Метрика |  Результат |
| ------- | ---------: |
| Hit@1   | **0.6250** |
| Hit@5   | **1.0000** |
| Hit@10  | **1.0000** |
| MRR@10  | **0.7937** |

На validation-выборке из 40 деклараций это означает:

- релевантная регуляция находится на первом месте в 25 случаях;
- релевантная регуляция находится в top-5 во всех 40 случаях;
- релевантная регуляция находится в top-10 во всех 40 случаях.

При этом размер validation-выборки невелик, поэтому результаты следует
рассматривать как ориентир для выбора подхода, а не как статистически
устойчивую оценку качества на всей выборке.

После этого этапа дальнейший перебор sparse-конфигураций прекращается,
чтобы снизить риск подгонки под локальную validation-выборку.

## 8. Dense retrieval

После экспериментов со sparse-представлениями был исследован подход на основе
плотных (dense) эмбеддингов.

В качестве embedding-модели использовалась
`intfloat/multilingual-e5-base`, ориентированная на задачи
семантического поиска. Для E5 использовался рекомендованный формат запросов:

- декларация: `query: <text>`;
- регуляция: `passage: <text>`.

Для декларации использовались поля `G31_1` и `desc_extention`.

Для регуляций отдельно исследовалось влияние различных комбинаций полей:

- `description`;
- `description + explanation`;
- `description + notes`;
- `description + explanation + notes`.

Эмбеддинги нормализовались, после чего релевантность определялась через
скалярное произведение, эквивалентное cosine similarity для нормализованных
векторов.

### 8.1. E5-base

Результаты экспериментов:

| Модель | Hit@1 | Hit@5 | Hit@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| E5 + description | 0.4500 | 0.8000 | 0.8250 | 0.5748 |
| E5 + description + explanation | 0.4000 | 0.8500 | 0.9000 | 0.5681 |
| E5 + description + notes | 0.2750 | 0.5000 | 0.7500 | 0.4023 |
| E5 + all fields | 0.3000 | 0.5750 | 0.7500 | 0.4429 |

Наилучший результат по MRR@10 показал вариант только с полем
`description`:

- Hit@1 = 0.4500;
- Hit@5 = 0.8000;
- Hit@10 = 0.8250;
- MRR@10 = 0.5748.

Добавление `explanation` позволило увеличить Hit@5 и Hit@10, однако
снизило Hit@1 и MRR@10.

Добавление `notes` существенно ухудшило качество. Вероятная причина —
наличие в `notes` большого количества общих нормативных текстов, которые
повторяются между различными регуляциями и добавляют шум в семантическое
представление.

Использование всех доступных полей также оказалось хуже базового варианта
с `description`. Таким образом, увеличение объёма контекста не гарантирует
улучшения качества retrieval.

### 8.2. E5-large

После этого был проведён аналогичный эксперимент с более крупной моделью
`intfloat/multilingual-e5-large`.

Результаты:

| Model | Hit@1 | Hit@5 | Hit@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| E5-large + description | 0.5750 | 0.8750 | 0.9500 | 0.7130 |
| E5-large + description + explanation | 0.6000 | 0.9000 | 0.9000 | 0.7204 |
| E5-large + description + notes | 0.4500 | 0.8500 | 0.9000 | 0.6152 |
| E5-large + all fields | 0.4000 | 0.8250 | 0.9250 | 0.6094 |

По сравнению с `E5-base` переход на `E5-large` дал существенный прирост
качества.

Для варианта с `description`:

| Model | Hit@1 | Hit@5 | Hit@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| E5-base | 0.4500 | 0.8000 | 0.8250 | 0.5748 |
| E5-large | 0.5750 | 0.8750 | 0.9500 | 0.7130 |

Таким образом, увеличение размера embedding-модели в данном случае
существенно улучшило качество семантического поиска.

Лучшим вариантом среди протестированных конфигураций E5-large стал:

`description + explanation`

с результатами:

- Hit@1 = 0.6000;
- Hit@5 = 0.9000;
- Hit@10 = 0.9000;
- MRR@10 = 0.7204.

Интересно, что в случае E5-large добавление `explanation`, в отличие от
E5-base, уже немного улучшило MRR@10 и Hit@1.

При этом `notes` и полное объединение всех полей по-прежнему уступают
вариантам без `notes`.

### 8.3. Сравнение sparse и dense подходов

На текущем этапе лучший sparse-вариант остаётся сильнее лучшего dense-варианта
на локальной validation-выборке.

Лучший sparse-вариант:

`TF-IDF char_wb (3-5) + нормализация`

| Method | Hit@1 | Hit@5 | Hit@10 | MRR@10 |
| --- | ---: | ---: | ---: | ---: |
| TF-IDF char_wb 3-5 + normalization | **0.6250** | **1.0000** | **1.0000** | **0.7937** |
| E5-large + description + explanation | 0.6000 | 0.9000 | 0.9000 | 0.7204 |

Таким образом, на данной validation-выборке sparse-подход превосходит
dense-подход по всем четырём рассматриваемым метрикам.

При этом E5-large показывает существенно лучший результат, чем E5-base,
поэтому dense-представления сохраняют практический интерес как источник
дополнительного семантического сигнала.

Это приводит к следующей гипотезе:

> TF-IDF хорошо учитывает точные лексические совпадения и морфологические
> особенности терминов, тогда как dense-модель способна учитывать
> семантическое сходство текстов. Объединение двух типов ранжирования может
> позволить получить более устойчивый результат.

В следующем эксперименте поэтому рассматривается гибридный подход,
объединяющий результаты sparse и dense retrieval.

## 9. Гибридный поиск (Hybrid Retrieval)

После сравнения sparse- и dense-подходов был проведён эксперимент с их объединением.

### 9.1. Используемые модели

В качестве sparse-модели использовался TF-IDF с символьными n-граммами:

- `analyzer="char_wb"`
- `ngram_range=(3, 5)`
- `sublinear_tf=True`
- предварительная нормализация текста

Для dense retrieval использовалась модель:

- `intfloat/multilingual-e5-large`

Для E5 использовался retrieval-формат:

```text
query: <текст декларации>
passage: <текст регуляции>
```

Для декларации использовались поля:

```text
G31_1 + desc_extention
```

Для регуляции:

```text
description + explanation
```

Для TF-IDF использовалось только поле:

```text
description
```

---

### 9.2. Индивидуальные результаты

Перед объединением были зафиксированы результаты отдельных моделей.

| Модель   |  Hit@1 |  Hit@5 | Hit@10 | MRR@10 |
| -------- | -----: | -----: | -----: | -----: |
| TF-IDF   | 0.6250 | 1.0000 | 1.0000 | 0.7937 |
| E5-large | 0.6000 | 0.9000 | 0.9000 | 0.7204 |

TF-IDF показывает лучший результат среди отдельных моделей:

- `Hit@1 = 0.6250`
- `MRR@10 = 0.7937`
- `Hit@10 = 1.0000`

При этом E5-large использует другой тип семантического представления текста и потенциально может исправлять ошибки TF-IDF.

---

### 9.3. Reciprocal Rank Fusion

Для объединения результатов использовался метод **Reciprocal Rank Fusion (RRF)**.

RRF объединяет несколько ranking'ов, не требуя напрямую сравнивать значения similarity различных моделей.

Для документа `d`:

$$
RRF(d) = \sum_m \frac{1}{k + rank_m(d)}
$$

где:

- $rank_m(d)$ — позиция документа в ranking модели $m$;
- $k$ — параметр сглаживания;
- $m$ — одна из используемых retrieval-моделей.

В эксперименте объединялись:

```text
TF-IDF ranking
       +
E5-large ranking
       ↓
      RRF
       ↓
финальный ranking
```

---

### 9.4. Базовый эксперимент RRF

Сначала использовалось стандартное значение:

```text
k = 60
```

Результат:

| Метод      |  Hit@1 |  Hit@5 | Hit@10 | MRR@10 |
| ---------- | -----: | -----: | -----: | -----: |
| TF-IDF     | 0.6250 | 1.0000 | 1.0000 | 0.7937 |
| E5-large   | 0.6000 | 0.9000 | 0.9000 | 0.7204 |
| RRF (k=60) | 0.6500 | 0.9250 | 0.9750 | 0.7865 |

При `k=60` RRF увеличил `Hit@1` относительно TF-IDF:

```text
0.6250 → 0.6500
```

Однако `MRR@10` немного снизился:

```text
0.7937 → 0.7865
```

Поэтому было решено дополнительно исследовать влияние параметра `k`.

---

### 9.5. Эксперимент с параметром k

Были протестированы следующие значения:

```text
k = 1, 5, 10, 20, 40, 60, 100, 200
```

Результаты:

|     k |      Hit@1 |      Hit@5 |     Hit@10 |     MRR@10 |
| ----: | ---------: | ---------: | ---------: | ---------: |
|     1 |     0.6750 |     0.9750 |     1.0000 |     0.8040 |
| **5** | **0.6750** | **0.9750** | **1.0000** | **0.8044** |
|    10 |     0.6500 |     0.9500 |     1.0000 |     0.7909 |
|    20 |     0.6750 |     0.9500 |     0.9750 |     0.8002 |
|    40 |     0.6750 |     0.9250 |     0.9750 |     0.8000 |
|    60 |     0.6500 |     0.9250 |     0.9750 |     0.7865 |
|   100 |     0.6500 |     0.9250 |     0.9750 |     0.7861 |
|   200 |     0.6750 |     0.9250 |     0.9750 |     0.7986 |

На используемой validation-выборке наилучший результат показал:

```text
k = 5
```

---

### 9.6. Лучший результат hybrid retrieval

Итоговая конфигурация:

```text
TF-IDF
  +
multilingual-e5-large
  +
RRF (k=5)
```

Результат:

```text
Hit@1:  0.6750
Hit@5:  0.9750
Hit@10: 1.0000
MRR@10: 0.8044
```

По сравнению с лучшим TF-IDF:

| Метрика | TF-IDF | Hybrid RRF |   Изменение |
| ------- | -----: | ---------: | ----------: |
| Hit@1   | 0.6250 | **0.6750** | **+0.0500** |
| Hit@5   | 1.0000 |     0.9750 |     -0.0250 |
| Hit@10  | 1.0000 |     1.0000 |           0 |
| MRR@10  | 0.7937 | **0.8044** | **+0.0107** |

Таким образом, hybrid-подход позволил увеличить:

- `Hit@1` на **5 п.п.**;
- `MRR@10` на **0.0107**;

при сохранении `Hit@10 = 1.0`.

---

### 9.7. Вывод

На текущей validation-выборке объединение sparse и dense retrieval показало лучший результат, чем использование каждой модели отдельно.

Лучшей конфигурацией стала:

```text
TF-IDF char_wb (3-5)
        +
multilingual-e5-large
        +
RRF (k=5)
```

Итоговые метрики:

```text
Hit@1:  0.6750
Hit@5:  0.9750
Hit@10: 1.0000
MRR@10: 0.8044
```

При этом размер validation-выборки составляет всего 40 деклараций, поэтому выбор `k=5` следует рассматривать как результат эксперимента на текущей выборке, а не как универсально оптимальное значение.

---

## 10. Анализ ошибок Hybrid Retrieval

После выбора итоговой конфигурации hybrid retrieval:

```text
TF-IDF char_wb (3-5)
        +
multilingual-e5-large
        +
RRF (k=5)
```

был проведён дополнительный анализ ошибок на validation-выборке.

Цель анализа — определение характера оставшихся ошибок и понимание того, какие признаки декларации недостаточно хорошо учитываются текущими retrieval-моделями.

---

### 10.1. Методика анализа

Для каждой декларации сравнивался ранг правильной регуляции в трёх ranking'ах:

- TF-IDF;
- E5-large;
- RRF.

Особое внимание уделялось случаям, когда ни один из retrieval-подходов не помещал правильную регуляцию на первое место.

Такие случаи были классифицированы как:

```text
BOTH_WRONG
```

При этом важно различать:

```text
retrieval error
```

и

```text
semantic ambiguity between neighboring regulations
```

Во многих рассмотренных случаях правильная регуляция присутствует среди Top-3, однако модель выбирает на первое место очень близкую регуляцию, отличающуюся одним или несколькими специфическими признаками товара.

Таким образом, основная проблема текущего retrieval заключается не только в поиске релевантного документа, но и в различении близких нормативных позиций.

---

### 10.2. Общая картина ошибок

В рассмотренных ошибках наблюдается характерная закономерность:

> Retrieval хорошо определяет общий товарный класс, но не всегда корректно учитывает признаки, определяющие конкретную товарную подсубпозицию.

Например, система правильно распознаёт:

- свинину;
- газойль;
- комбинезон;
- кефир;
- PHEV-автомобиль;
- химическое вещество;
- древесный шпон;

но ошибается при выборе между несколькими регуляциями внутри одного товарного класса.

Это особенно заметно там, где регуляции отличаются небольшими, но юридически значимыми признаками:

```text
содержание серы
возраст автомобиля
объём двигателя
назначение товара
пол потребителя
тип упаковки
наличие специальных компонентов
химическая структура
```

---

### 10.3. Пример ошибки 1: свинина

#### Declaration

```text
СВИНИНА МОРОЖЕНАЯ:
РЕБЕРНЫЕ ОТРУБЫ ДОМАШНИХ СВИНЕЙ НА КОСТИ,
НЕТТО 105 КГ...
```

Правильная регуляция:

```text
R0002
```

Результаты:

| Метод    | Ранг R0002 |
| -------- | ---------: |
| TF-IDF   |          2 |
| E5-large |          3 |
| RRF      |          2 |

При этом первое место во всех случаях занимает:

```text
R0003
```

Регуляции R0002 и R0003 относятся к одному и тому же товарному классу и имеют практически идентичное нормативное описание.

В данном случае retrieval корректно определяет предметную область, но не способен надёжно разрешить тонкое различие между соседними позициями.

---

### 10.4. Пример ошибки 2: концентрация для напитков

Для декларации:

```text
КОНЦЕНТРАТ COLA BASE C-17...
САХАРОЗА 12,0 МАС.%,
ГЛЮКОЗА 6,0 МАС.%...
```

правильной является:

```text
R0126
```

TF-IDF помещает её на третье место:

```text
R0125
R0124
R0126  ← correct
```

E5-large также не ставит правильную регуляцию на первое место.

Здесь критическими являются количественные ограничения по составу:

```text
сахароза
глюкоза
содержание спирта
```

Однако обычный semantic retrieval воспринимает документы прежде всего как тексты и не выполняет полноценное логическое сравнение числовых условий.

Это показывает важное ограничение текущего подхода:

> **Retrieval не заменяет проверку нормативных условий.**

---

### 10.5. Пример ошибки 3: древесный шпон

Для строганого шпона из шореи:

```text
ТОЛЩИНА 2,0 ММ
ШИРИНА 300 ММ
ДЛИНА 2200 ММ
...
```

правильная регуляция:

```text
R0149
```

Все три метода ставят её только на третье место.

При этом первые два результата относятся к очень близким категориям:

```text
R0150 — прочие листы для облицовки...

R0148 — клееная фанера...

R0149 — прочие листы для облицовки,
        полученные разделением слоистой древесины...
```

То есть retrieval правильно определяет:

```text
древесина
→ тропическая древесина
→ шорея
→ облицовочные листы
```

но не может надёжно определить способ получения материала, который является критическим для классификации.

---

### 10.6. Пример ошибки 4: газойль

Для декларации:

```text
ГАЗОЙЛЬ НЕФТЯНОЙ...
СЕРА 0,12 МАС.%
БИОДИЗЕЛЬ НЕ СОДЕРЖИТ
```

правильная регуляция:

```text
R0086
```

Однако первой становится:

```text
R0087
```

Главное различие между ними:

```text
R0086:
0,05% < S ≤ 0,2%

R0087:
S > 0,2%
```

В декларации явно указано:

```text
S = 0,12%
```

То есть семантически обе регуляции чрезвычайно близки, но правильный выбор определяется **числовым условием**.

Это один из наиболее показательных примеров того, почему дальнейшее повышение качества системы нельзя полностью решить только улучшением embedding-модели.

---

### 10.7. Пример ошибки 5: одежда

Для мужского комбинезона:

```text
100% ПОЛИЭСТЕР
...
НЕ ЯВЛЯЕТСЯ ПРОИЗВОДСТВЕННОЙ СПЕЦОДЕЖДОЙ
```

правильная регуляция:

```text
R0186
```

Однако все методы ставят выше:

```text
R0185
```

Разница между регуляциями:

```text
R0185 — производственные и профессиональные комбинезоны

R0186 — прочие комбинезоны
```

В декларации есть явный признак:

```text
НЕ ЯВЛЯЕТСЯ ПРОИЗВОДСТВЕННОЙ СПЕЦОДЕЖДОЙ
```

Но retrieval не использует это отрицательное утверждение достаточно эффективно.

Это указывает на отдельный класс проблем:

> **Отрицательные признаки и условия-исключения могут иметь большую классификационную ценность, чем общие описательные признаки товара.**

---

### 10.8. Пример ошибки 6: кефир

Для детского кефира:

```text
КЕФИР ДЕТСКИЙ...
ПЕРВИЧНАЯ УПАКОВКА 0,20 Л
ДЛЯ ПИТАНИЯ ДЕТЕЙ С 8 МЕСЯЦЕВ
```

правильная регуляция:

```text
R0029
```

Однако все методы ставят первой:

```text
R0028
```

Причина особенно интересна: R0028 содержит очень похожее описание и дополнительно явно упоминает:

```text
для детского питания
```

При этом правильная регуляция R0029 является более общей:

```text
Прочий кефир...
```

Таким образом, retrieval имеет тенденцию предпочитать документ, содержащий **больше буквального совпадения с отдельными признаками декларации**, даже если нормативная классификация требует выбрать более общую позицию.

---

### 10.9. Пример ошибки 7: PHEV-автомобиль

Для автомобиля:

```text
PHEV
1598 см³
2020 год
бывший в эксплуатации
```

правильная регуляция:

```text
R0319
```

Все методы выбирают близкие позиции:

```text
R0316
R0318
R0317
```

Все они относятся к одному классу:

```text
8703 60
```

и отличаются преимущественно дополнительными условиями:

```text
возраст автомобиля
мощность ДВС
мощность электродвигателя
```

В данном случае особенно хорошо видно, что задача фактически превращается из:

```text
semantic retrieval
```

в:

```text
attribute extraction
        +
rule matching
        +
fine-grained ranking
```

---

### 10.10. Характерные типы ошибок

По рассмотренным случаям ошибки можно условно разделить на несколько категорий.

#### 1. Соседние нормативные позиции

Несколько регуляций описывают практически один и тот же товар, но отличаются одним специфическим признаком.

Примеры:

```text
R0002 vs R0003
R0178 vs R0179
R0317 vs R0319
```

---

#### 2. Числовые пороги

Правильный выбор определяется диапазоном числового значения:

```text
содержание серы
массовая доля компонентов
объём двигателя
толщина
возраст
```

Пример:

```text
0.05 < S ≤ 0.2
```

Semantic similarity не гарантирует корректного сопоставления такого условия.

---

#### 3. Отрицательные признаки

В декларации может присутствовать условие:

```text
не является производственной спецодеждой
```

или:

```text
не содержит биодизель
```

Для классификации это может быть критически важно, но для retrieval отрицание может иметь меньший вес, чем совпадающие слова:

```text
комбинезон
синтетические нити
мужской
```

---

#### 4. Специфические атрибуты

Общий объект определяется правильно, но конкретный атрибут — нет.

Например:

```text
кефир
→ детское питание

автомобиль
→ PHEV + возраст + объём двигателя

шпон
→ способ получения

химическое вещество
→ конкретное химическое соединение
```

---

#### 5. Перегрузка текстовыми совпадениями

Некоторые документы содержат большое количество общих совпадений с декларацией.

Особенно это заметно для длинных нормативных описаний.

В результате модель может предпочесть документ, который:

```text
лексически похож
```

но не соответствует всем условиям классификации.

---

### 10.11. Основной вывод анализа ошибок

Проведённый анализ показывает, что текущий hybrid retrieval уже хорошо решает задачу поиска релевантного товарного класса, но основная сложность находится на следующем уровне, fine-grained classification: числовые условия, диапазоны, отрицания, специальные признаки, исключения, иерархия ТН ВЭД. Дальнейшее улучшение качества, вероятно, потребует не простого увеличения `Top-K` или замены одной embedding-модели другой.

---

### 10.13. Направления дальнейшего улучшения

На основании анализа ошибок наиболее перспективными направлениями являются:

#### 1. Reranking

Reranker может учитывать взаимодействие между всей декларацией и конкретной регуляцией лучше, чем независимые embedding-векторы.

---

#### 2. Извлечение структурированных признаков

Из декларации можно отдельно извлекать:

```text
товар
материал
состав
назначение
пол
возраст
объём
масса
толщина
содержание компонентов
CAS
тип двигателя
мощность
```

После этого эти признаки могут использоваться при reranking.

---

#### 3. Rule-based post-processing

Для некоторых классов товаров правила могут быть эффективнее дополнительного semantic retrieval.

Например:

```text
если sulfur = 0.12%
→ исключить регуляции sulfur > 0.2%
```

или:

```text
если "не является производственной спецодеждой"
→ исключить professional/workwear
```

---

#### 4. Иерархический retrieval

Вместо поиска непосредственно среди всех регуляций:

```text
все регуляции
      ↓
группа
      ↓
товарная позиция
      ↓
субпозиция
      ↓
конкретная регуляция
```

Это особенно актуально для ТН ВЭД, где регуляции образуют естественную иерархию.

---

### 10.14. Итоговое состояние эксперимента

На текущем этапе эксперименты с базовыми retrieval-подходами считаются завершёнными.

Финальная конфигурация:

```text
                  Declaration
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        TF-IDF char_wb      E5-large
          (3-5)                │
             │                  │
             └────────┬─────────┘
                      ▼
                  RRF (k=5)
                      │
                      ▼
                   Top-K
                      │
                      ▼
               candidate set
```

Полученные метрики на validation-выборке:

| Метрика    |  Результат |
| ---------- | ---------: |
| **Hit@1**  | **0.6750** |
| **Hit@5**  | **0.9750** |
| **Hit@10** | **1.0000** |
| **MRR@10** | **0.8044** |

Таким образом, в 97.5% случаев правильная регуляция находится в Top-5, а в 100% — в Top-10.

Это позволяет перейти от задачи поиска по всей базе регуляций к следующему этапу — reranking и fine-grained классификации ограниченного набора кандидатов.

При этом результаты получены на validation-выборке из 40 деклараций, поэтому они используются прежде всего для выбора направления дальнейшей разработки, а не как окончательная оценка качества production-системы.
